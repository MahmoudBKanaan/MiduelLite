3. PROJECT PROBLEM
================================================================================
Online users may wish to participate in short intellectual interactions with another person
without creating an account, maintaining a permanent profile, building social connections
or using a complicated platform.
Many multiplayer systems require registration, authentication, profile management,
ranking systems and other persistent functionality before a user can participate.
Minduel Lite addresses this by providing an extremely lightweight interaction:
1. create an anonymous temporary profile,
2. select three interests,
3. enter a matchmaking pool,
4. be matched with a compatible player,
5. answer ten questions,
6. score the opponent's answers,
7. obtain a match result,
8. optionally play again.

16. INTEREST VECTOR MODEL
================================================================================
Each user selects exactly 3 interests from 32.
The profile can therefore be represented as a 32-dimensional binary vector.
Example:
Player A:
Technology
Science
Philosophy
Vector conceptually:
[1,0,0,1,0,0,0,1,0,...]
Player B:
Technology
Science
History
Vector:
[1,0,0,1,0,0,0,0,0,1,...]
Shared interests:
2
Because every player has exactly three selected interests, complex vector mathematics is
unnecessary.
Similarity is:
sharedInterestCount = number of identical interest IDs
Possible values:
3 = strongest compatibility
2 = strong compatibility
1 = acceptable compatibility
0 = incompatible
For academic explanation, normalized similarity may be presented as:
similarity = sharedInterestCount / 3
Therefore:
3 shared = 1.00
2 shared = 0.67
1 shared = 0.33
0 shared = 0.00
No machine learning is involved.
No vector database is involved.
No embedding model is involved.

17. MATCHMAKING ALGORITHM
================================================================================
When a player joins the queue:
STEP 1
Retrieve all waiting players except the current player.
STEP 2
Calculate shared interest count against every candidate.
STEP 3
Discard candidates sharing zero interests.
STEP 4
Find the candidate with the greatest sharedInterestCount.
Priority:
3 shared interests
then
2 shared interests
then
1 shared interest.
STEP 5
If multiple players have identical compatibility:
match the player who entered the queue earliest.
STEP 6
Create match.
STEP 7
Remove both users from queue.
STEP 8
Return match ID.
Pseudo-code:
candidates = waitingPlayers excluding currentPlayer
for candidate in candidates:
    overlap = countSharedInterests(
        currentPlayer.interests,
        candidate.interests
    )
eligible = candidates where overlap >= 1
sort eligible by:
    overlap DESC
    joinedAt ASC
bestCandidate = first eligible candidate
if bestCandidate exists:
    createMatch(currentPlayer, bestCandidate)
else:
    addCurrentPlayerToQueue()
IMPORTANT:
Users with zero shared interests are NOT matched.
They remain in the pool until a compatible user becomes available.

25. SCORE FLAGGING / STRIKING
================================================================================
A player may flag the score they received.
Example:
Player 2 gives Player 1:
Score = 3
Player 1 may select:
FLAG SCORE
The score then becomes:
flagged = true
A flagged score is STRUCK.
Struck scores are excluded from final score calculation.
A score can be flagged only once.
A review action becomes immutable after submission.
================================================================================
26. THREE-FLAG TERMINATION RULE
================================================================================
The match tracks:
totalFlagCount
This is the COMBINED number of flagged scores from both players.
Example:
Player 1 flags two received scores.
Player 2 flags one received score.
totalFlagCount = 3
When:
totalFlagCount >= 3
the match ends immediately.
End reason:
THREE_FLAGS
Remaining questions are not played.
================================================================================
27. NORMAL MATCH TERMINATION
================================================================================
The match ends normally after:
Question 10
has completed:
- Player 1 answer,
- Player 2 score,
- Player 2 answer,
- Player 1 score,
- both score reviews.
End reason:
COMPLETED
================================================================================
28. FINAL SCORE CALCULATION
================================================================================
Only non-flagged received scores are included.
For Player 1:
validPlayer1Scores =
scores assigned to Player 1
where flagged = false
Player 1 final score:
average(validPlayer1Scores)
For Player 2:
validPlayer2Scores =
scores assigned to Player 2
where flagged = false
Player 2 final score:
average(validPlayer2Scores)
Use average rather than raw total because flagged scores may result in the players having
different numbers of valid scores.
Round to:
1 decimal place.
Example:
Player 1 valid scores:
8, 7, 9, 8, 7
Average:
7.8
Player 2 valid scores:
6, 8, 6, 7, 7
Average:
6.8
Winner:
Player 1
If averages are identical:
DRAW
If a player somehow has zero valid scores:
final score = 0

Examples:
Use REST instead of GraphQL.
Use polling instead of WebSockets.
Use PostgreSQL arrays instead of an interest join table.
Use direct SQL instead of an ORM.
Use four screens instead of a large navigation structure.
Use anonymous sessions instead of accounts.
Use static avatars instead of uploads.
Use seeded questions instead of question administration.
Use one backend instead of microservices.
Use local Docker instead of cloud infrastructure.
Use peer scores instead of AI evaluation.

================================================================================

1. Is it explicitly required by IU?
OR
2. Is it necessary for one of the acceptance criteria?
If both answers are NO:
DO NOT IMPLEMENT IT.
